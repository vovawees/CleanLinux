# Rolling release+++

Обычный rolling release — «всегда свежие версии, но обновление может сломать систему».
CleanLinux берёт свежесть rolling и добавляет к ней то, чего обычно не хватает source-based дистрибутивам: **предсказуемость, атомарность на уровне сборки, контроль ABI и откат**.

## Что делает `burn update`

```
sync ─► plan ─► build ALL ─► snapshot + pre-update hooks ─► apply ─► ABI follow-up ─► post-update hooks ─► doctor
                   │                (btrfs)                          │
                   └─ ошибка сборки: система не тронута               └─ пересборка зависимых, preserved libs
```

1. **sync** — `git fetch` репозиториев рецептов на канале `CHANNEL` (только fast-forward).
2. **plan** — для каждого установленного пакета: `upgrade`, `downgrade`, `rebuild: recipe or features changed`, `held`, `orphan`. Метки риска: `major` (сменилась первая цифра версии) и `core` (пакет из `CORE_PKGS`: glibc, gcc, binutils, linux, mesa, llvm). Ниже — история изменений рецептов из git с прошлого обновления.
3. **build ALL** — все пакеты собираются в кеш в порядке зависимостей. Если хоть один не собрался, обновление прерывается **до** изменения системы.
4. **snapshot + pre-update hooks** — точка отката. Если корень — подтом btrfs, burn сам делает read-only снимок `/.snapshots/burn-<время>` (ioctl ядра, без btrfs-progs; хранятся последние `SNAPSHOTS=5` из `burn.conf`, `0` — без снимков; вручную — `burn snapshot`), потом запускает хуки `/etc/burn/hooks/pre-update.d/`. Ошибка снимка или pre-хука останавливает обновление.
5. **apply** — установка собранных пакетов; удалённые из пакета файлы чистятся, конфиги из `backup` не перезаписываются (новая версия ложится как `.burnnew`).
6. **ABI follow-up** — если у библиотеки пропала soname (например, `libfoo.so.1` → `libfoo.so.2`):
   - старая библиотека остаётся на месте как **preserved** — уже установленные программы продолжают работать;
   - все пакеты, которым нужна старая soname (`needs-so`), автоматически пересобираются против новой;
   - preserved-библиотека удаляется, когда она больше никому не нужна.
7. **doctor** — проверка: нет ли пакетов с отсутствующими библиотеками, остались ли preserved-библиотеки.

Каждая транзакция пишется в `/var/lib/burn/state/history` (`дата|операция|пакет|было|стало|файл`).

## Предсказуемость

- **features вместо автодетекта.** Опциональные зависимости включаются явно (`features=(+wayland -x11)`), meson работает с `--auto-features=disabled`. Обновление не «подхватит» случайную библиотеку из системы.
- **ABI-aware кеш.** BUILDID включает soname библиотек, которые дают установленные зависимости. Пакет, собранный против старой ABI, не будет переиспользован после её смены.
- **`burn plan`** ничего не меняет и показывает ровно то, что сделает `update`.

## Откат и заморозка

```sh
burn rollback mesa     # вернуть предыдущую сборку mesa из кеша и заморозить её
burn hold linux        # не обновлять ядро
burn unhold linux
burn hold              # список замороженных
burn history           # журнал транзакций
```

Если сломалось что-то крупное — откат всей системы на btrfs-снимок, сделанный перед обновлением.

## Каналы

`CHANNEL` в `/etc/burn/burn.conf` — это ветка репозитория рецептов:

| Канал | Что там |
|---|---|
| `main` | по умолчанию: рецепты, прошедшие проверки `tools/check.sh` (lint, ссылки и sha256) |
| `edge` | новые версии upstream сразу после выхода: `tools/edge.sh` каждый день (cron у сопровождающего) запускает `tools/updates.sh --write`, проверяет ссылки и sha256 (`tools/lint.sh --fetch`), публикует в ветку `edge` и предлагает PR в `main` |
| `security` *(план)* | только исправления безопасности поверх `main` — для «поставил и забыл» |

### Откуда берутся новые версии

`tools/updates.sh` в CleanLinux-Recipes сам находит upstream по ссылкам рецепта — отдельных метаданных нет: листинги GNU и kernel.org (включая каталоги версий `gcc-X/`, `util-linux/vX.Y/`), stable-ядро из `releases.json`, GitHub releases (теги как запасной вариант), любые https-каталоги и официальные патчи bash/readline (`_patches=({001..NNN})`, версия — по числу патчей). `-v` показывает и актуальные рецепты, `--write` поднимает версию, сбрасывает `release=1`, скачивает исходники и переписывает `sha256=()`.

## Проверено тестами

`tests/rolling.sh` проверяет весь цикл на тестовой паре пакетов `libfoo` + `app` (без скачиваний): запись sha256 в рецепт, план с меткой `[major]`, обновление со сменой soname, автоматическую пересборку `app`, очистку preserved-библиотеки, `doctor`, `hold`/`unhold`, `rollback` из кеша и журнал истории.
